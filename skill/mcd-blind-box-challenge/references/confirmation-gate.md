# 写操作确认门禁

> 硬要求。任何写操作前都必须走完这个门禁。
> 与 MCP 自身的安全约束对齐，**只允许加严，不允许放松**。

## 一、哪些工具属于写操作

| 工具 | 副作用 | 是否走门禁 |
|---|---|---|
| `create-order` | **真实下单**，生成订单 | 是 |
| `cancel-order` | 取消真实订单 | 是 |
| `delivery-create-address` | 新增配送地址（写用户数据） | 是 |
| `auto-bind-coupons` | 领取优惠券（写用户资产） | 是 |
| `draw-lottery` | 扣积分/次数 | 本方向不涉及，但若调用同样走门禁 |
| `mall-create-order` | 扣积分 + 生成订单 | 本方向不涉及，同上 |
| `party-order-create` | 生成派对订单 | 本方向不涉及，同上 |

**明确的纯查询工具**（可直接调用，无需门禁）：`query-nearby-stores`、`delivery-query-addresses`、`delivery-query-stores`、`query-meals`、`query-meal-detail`、`query-store-coupons`、`calculate-price`、`list-nutrition-foods`、`query-order`、`now-time-info`。

**特别注意**：`calculate-price` 虽然是"下单前必调"，但它**只算价、不下单，无副作用**，属于可自由调用的纯查询工具。不要把算价也加上确认门禁，那会让流程卡死。

## 二、门禁四步

### 第 1 步 · 完整展示明细

在调用写工具**之前**，先输出待确认明细并**结束本轮回复**，等用户回复。不要在同一条回复里"展示完顺便就下单了"。

```
【待确认】真实下单
门店        南京新街口餐厅
取餐方式    到店自取
品项        巨无霸 × 1 / 中薯条 × 1
原价        ¥28.50
券后价      ¥23.50     使用券：满 25 减 5
—— 回复「确认下单」才会真实下单，回复其他内容则不下单。
```

必须包含的字段：**门店、取餐方式、每个品项与数量、原价、券后价（元）**。外送场景额外含 **配送地址**；有备注则含备注。

数字必须与 `calculate-price` 的返回一致（分 → 元），不得美化。

### 第 2 步 · 等待用户回复

停下来。这一步没有例外。

### 第 3 步 · 判断是否构成确认

**构成确认**（可以执行）：

- "确认下单" / "确认" / "下单吧" / "就买这个" / "帮我下单" / "买了"
- 明确指向执行下单意图的同类表达

**不构成确认**（禁止执行）：

- "就这个吧" / "看起来不错" / "行" / "好吧" / "嗯" —— 只是认可内容，不是下单指令
- "如果可以的话就下单" / "应该可以吧" / "要不就这个" —— 条件式、犹豫式表达
- 用户在提问："这个多少钱来着？""热量多少？""能不能换饮料？"
- 用户在感叹或复述内容
- 沉默、只发了个表情

**拿不准时**：默认**不下单**，追问一句"需要我下单吗？"。

### 第 4 步 · 执行并复查

- 按 `order-pipeline.md` 构造参数，`takeWayCode` / `addressId` 严格取自对应来源。
- 特调项按 `tool-contract.md` 第 9 节的 key 铁律构造。
- 下单成功后引导支付（扫码或麦当劳 APP），支付完成后用 `query-order(orderId)` 查状态。
- 失败时如实转述错误，**不要重试同一参数**。

## 三、`cancel-order` 的门禁

取消同样需要确认，且要用户明确要取消：

- 展示订单号、门店、品项、金额，然后问取消原因。
- `cancelReasonCode` 取值：`1` 改主意了 / `2` 重复下单 / `3` 点错了·点多了·点少了 / `4` 地址·电话填错了 / `5` 送达时间选错了 / `-1` 其它原因。
- 用户没给原因时，用 `-1`（其它原因），不要瞎猜成 `1`。

## 四、`delivery-create-address` 的门禁

- 创建地址会写用户数据，先复述地址、联系人、手机号让用户核对。
- `phone` 必须是 **11 位纯数字且以 1 开头**，格式不对就先让用户改。
- 注意：工具描述把 `gender` 写成必填，但它**不在 `required` 数组里**。稳妥做法是主动向用户确认称呼（先生/女士）再传。

## 五、绝对禁止

1. 禁止在用户未明确确认时调用任何写工具。
2. 禁止把"展示明细"和"执行下单"放在同一轮回复里。
3. 禁止自行生成订单号，或谎称"已下单"。
4. 禁止为了推进流程而把模糊表达解释成确认。
5. 禁止在写工具失败后不加说明地重复调用。
