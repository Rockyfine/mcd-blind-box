# 错误与降级手册

> 只在异常或玩法卡住时读。每个分支都给出"如实说明 + 可执行的下一步"，**不允许编造数据填补**。

## A. 门店相关

### A1. 用户没有收藏餐厅（`searchType=1` 返回空）

改用 `searchType=2`，并询问用户所在城市与位置关键词（两者都是必填）。

问法："你在哪个城市、附近有什么地标？我按位置搜一下。"

### A2. 位置搜不到门店

1. 请用户换个更宽泛的关键词（如"新街口" → "南京"）。
2. 仍为空：告知该位置附近没查到可点餐门店，建议用户直接打开麦当劳 APP 确认，或换一个城市/地标。

### A3. 门店不支持所选 `beType`

例如用户想要得来速，但 `query-nearby-stores(beType=5)` 返回空。

降级：告知该位置没查到支持得来速的门店，建议改成**到店自取**（`beType=1`）或**麦乐送**（`beType=2`）。**不要偷偷替用户换成自取然后当成功。**

### A4. 用户切换了取餐场景

旧的 `storeCode` / `beCode` 一律作废（`beCode` 与门店 + 取餐方式绑定）。必须重新查门店。

## B. 菜单相关

### B1. 门店无可售餐品

`query-meals` 返回空。

降级：告知该门店当前没有可取到的在售餐品，建议换门店或换取餐方式。

### B2. 候选集为空导致无法开盒

**禁止**凭记忆编一套"经典套餐"。正确做法：如实说明"这家店在售清单里没凑出符合条件的组合"，然后给两条出路 —— 换门店，或放宽约束（去掉预算/热量/口味限制）。

### B3. 约束太紧凑不出组合

例如"5 块钱要一份含饮料的套餐"。

1. 先说明当前最接近的方案是什么（花了多少、差多少）。
2. 再问是否放宽约束。
3. 用户坚持不放宽就明确说做不到，不要硬凑一个超预算的组合当成功。

### B4. `query-meals` 返回结构与预期不符

不要假设固定字段名。处理方式：按真实返回的字段读取；实在无法定位商品编码时，**降级为"列出候选让用户选"**，并说明自动盲盒这一步失败了。

### B5. 特调 key 报错

`calculate-price` 或 `create-order` 因特调参数报错时：

1. 回到 `query-meal-detail` 重新取 `selectedKey` / `unselectedKey`。
2. 检查是否满足了 key 铁律 —— **含 `unselectedKey` 的特调组，该组所有项都必须传**（不管选没选）。这是最常见的出错原因。
3. 仍失败：降级为**不带特调的默认配置**，并明确告知用户"特调没配上，是按默认款算的"。

## C. 优惠券相关

### C1. 门店没有可用券

按无券价展示即可。**不要**编造一个优惠，也不要拿卡包里的券顶上。

### C2. 券没抵扣上

先检查：是不是误用了 `query-my-coupons` 的券（它不校验门店/渠道可用性）。必须改用 `query-store-coupons` 的结果。

### C3. `query-my-coupons` 与 `query-store-coupons` 混淆

- `query-my-coupons` = 卡包资产，只看用户有什么券，**不承诺可用于当前订单**。
- `query-store-coupons` = 当前门店 + 订单类型下**真正可用**的券。

盲盒的券后价**只能**用后者。这个错误会让揭晓卡价格虚标。

## D. 外送相关

### D1. 用户没有配送地址

引导先创建：`delivery-create-address`（**写操作，走确认门禁**）。需要地址、门牌号、城市、联系人、手机号（11 位纯数字且以 1 开头）、称呼。

### D2. 地址不在配送范围

告知该地址没查到可配送门店，建议换地址或改到店自取。

### D3. 备注超长

`remark` 最多 50 字。超了就请用户精简，不要自行截断。

## E. 下单相关

### E1. 下单失败

如实转述错误信息，说明哪些参数可能有问题。**不要重试同一参数**。

常见原因自查：
- `beType=1` 却传了 `beCode`（到店自取绝对不能传）
- `orderType=2` 却缺 `addressId`
- `takeWayCode` 不是取自那次 `calculate-price` 的 `takeWayList[].code`
- `beCode` 与 `storeCode` 不是同一家门店

### E2. 用户支付后要查状态

用 `query-order(orderId)`。用户说"支付完成"或"支付失败"时都查一次最新状态。

### E3. 用户要取消

走 `cancel-order` 的确认门禁，见 `confirmation-gate.md` 第三节。原因不明时用 `-1`。

## F. 玩法相关

### F1. 营养数据匹配不上

`list-nutrition-foods` 的条目与门店菜单名对不上时：

**降级为不显示热量**，并说明"这份的热量没在营养表里匹配到"。

**绝对禁止**凭印象估一个热量数字填进去，也不要按同类别餐品"推算"。

### F2. 口味关键词零匹配

换同义词再试一次（如"辣" → "香辣/麻辣"）；仍为零就降级：告知没匹配到该口味，问是否换口味或改成纯盲盒。

### F3. 用户对抽到的盲盒不满意

不要偷偷重抽换一个来讨好用户。正确处理：说明这是随机结果，问要不要**重新开一盒**（明确说会换新种子），或改成指定点餐。

### F4. 用户要一次开多个

先确认是否真的要开多个（每个都是独立的一套，都会各自算价）。确认后再依次开，每盒之间换种子。

## G. 系统相关

### G1. MCP 服务不可用

直接告知用户 `mcd-mcp` 当前不可用，建议检查 MCP 配置或稍后重试。**不要凭记忆编造菜单、价格或门店。**

### G2. 鉴权失败

如实转述错误，说明可能需要重新授权。**不要重试同一参数**。

### G3. 工具返回超时

重试**一次**即可；仍失败就如实告知并停止，不要反复重试。
