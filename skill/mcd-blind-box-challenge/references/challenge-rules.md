# 盲盒规则与揭晓卡

> 玩法层。这是迭代最频繁的部分 —— 改玩法只改这个文件，不用动工具规则。

## 一、四种挑战模式

| 模式 | 用户会怎么说 | 约束 | 需要额外工具 |
|---|---|---|---|
| **纯盲盒** | "开个盲盒""随便点""给我惊喜" | 无价格约束，只要门店在售 | 无 |
| **预算挑战** | "30 块以内""别超过 25" | 券后价 ≤ 预算上限 | 无 |
| **热量挑战** | "不超过 600 大卡""来个低卡套餐" | 组合总热量 ≤ 上限 | `list-nutrition-foods` |
| **口味挑战** | "要辣的""想吃鸡""来个牛肉的""素的" | 餐品命中口味关键词 | 无 |

**模式可叠加**：例如"30 块以内要辣的" = 预算挑战 + 口味挑战。叠加时约束取交集。

**未指定模式**：默认走纯盲盒，但在 Step 0 用一句话说明可选模式（"要加挑战吗？有预算/热量/口味三种"），不要长篇大论列菜单。

## 二、随机策略（必须可验证）

不写脚本，但随机不能是"假装随机"。用服务器时间戳做种子：

1. 调用 `now-time-info()` 拿毫秒时间戳 `ts`（这是服务端时间，可核验）。
2. 把候选集按 `productCode` **升序排序**，得到稳定序号 `0 .. N-1`（排序保证同样的 `ts` 必然落到同一项，随机可复现）。
3. 主品索引 `i = ts mod N`。
4. 需要配品时，用 `floor(ts / N)` 作为新种子，对**剔除主品后的**候选集重复步骤 2-3。不要反复用 `ts mod N`，否则永远抽到相邻项。
5. 在揭晓卡底部用一行小字说明抽取依据，例如"种子 1789…4321 → 第 7 项"。**这让随机是真的可以被验证的，而不是嘴上说说。**

> **配品池的一处明确**：第 4 步里的"候选集"在抽取**配品**时取**非主食类**（小食 / 甜点 / 饮料）。
> 原因是第 3 节的「组合骨架」把配品定义为小食 / 薯条 / 饮料，揭晓卡也是按「主品 / 配品」两栏
> 渲染的；若照字面在含其他主食的集合里抽，会经常抽出"两个汉堡"，其中一个还被标成"配品"，
> 玩家会直接当成 bug。只有当非主食类为空（例如门店在售清单全是主食）时才回退到完整剔除集。

**约束不满足时的处理顺序**（逐级放宽，每级都要向用户说明）：

1. 先淘汰不符合约束的候选，只在剩余集合里抽（**这一步必须在抽取之前完成**：
   预算挑战要先按券后价估算、热量挑战要先按累计热量估算，把不可能满足约束的
   配品从候选池里剔掉，再对剩余集合取模。只在抽完之后评估，会经常抽出一套
   本来可以避开的超限组合，再靠下一步"已放宽"兜底 —— 那既不必要，也让用户
   觉得这把不算数）。
2. 剩余集合为空 → 放宽到"尽量接近约束"（预算挑战取最接近上限的组合，热量挑战取最低热量组合），并明确告知"没能在约束内凑出，这是最接近的一套"。
3. 仍然凑不出（例如候选集本身为空）→ 走 `troubleshooting.md` 的降级分支。

**禁止**：候选集为空时凭记忆编一套"经典套餐"；约束达不到时假装达到了。

## 三、组合骨架

盲盒默认抽**一份主品 + 可选配品**，不要一次抽一大桌。

**纯盲盒 / 口味挑战**：1 份主品（汉堡/卷/主食）即可，允许带 1 份配品。

**预算挑战**配品建议（**参考区间，不是硬规则** —— 优先服从真实菜单与价格）：

| 预算区间 | 搭配骨架 |
|---|---|
| 20 元以下 | 主品 + 小食 |
| 20–30 元 | 主品 + 小食，或主品 + 饮料 |
| 30–40 元 | 主品 + 薯条/小食 + 饮料 |
| 40–50 元 | 主品 + 薯条 + 小食 + 饮料 |
| 50 元以上 | 丰富组合，**优先不重复小食** |

**热量挑战**：以"总量不超上限"为唯一优先级，搭配骨架让位于热量约束。

**口味挑战的关键词映射**（模糊匹配餐品名称，匹配不上就换词或降级）：

| 用户说的 | 匹配关键词 |
|---|---|
| 辣 | 辣、香辣、麻辣、藤椒、火辣 |
| 鸡 | 鸡、鸡块、鸡翅、麦乐鸡 |
| 牛 | 牛、牛肉、双层牛 |
| 鱼 | 鱼、鳕鱼、鱼堡 |
| 素 | 蔬、素、沙拉、玉米、派 |
| 甜 | 派、冰淇淋、圣代、麦旋风、甜筒 |
| 咖啡 | 咖啡、拿铁、美式、麦咖啡 |

**匹配失败必须降级说明**，不要硬套一个不相干的商品顶上。例如："这家店在售清单里没匹配到'辣'的，要不要换成'鸡'或者干脆纯盲盒？"

**热量挑战版**

```
【麦门盲盒 · 热量挑战】

上限      600 大卡
实际      约 520 大卡  →  剩余 80
状态      挑战成功

主品  xxx × 1
配品  xxx × 1

门店      南京新街口餐厅（到店自取）
```

**揭晓卡必须包含**：品项与数量、原价、**券后价（元）**、门店与取餐方式、"回复确认下单才会真实下单"这句提示。热量挑战额外含热量与免责声明。

**注意**：所有数字必须与 `calculate-price` 返回一致（记得 /100），所有品项必须真实存在于 `query-meals` 返回中。

## 五、彩蛋与分享文案模板

每张揭晓卡配**一句**点评。保持克制，一次一句。

**可用的梗方向**
- 玄学叙事："服务器在 4321 毫秒时点了点头，于是有了这顿。"
- 预算反差："你的 30 块被我花掉了 23.5，剩下 6.5 请自行骄傲。"
- 热量自嘲："这份 520 大卡，是今天唯一一件我能控制的事。"（配免责声明）
- 口味认可："辣度达标，本盲盒官批准。"

**禁止**：承诺中奖/优惠/好吃；贬低用户或引发身材焦虑；对营养数据做减脂、疗效类表述。

**分享文案**（用户要"发朋友圈的话"时生成，纯文本）：

```
今天把点餐交给了服务器。它给我开了个盲盒：
巨无霸 + 中薯条，券后 ¥23.50。
在 30 块的预算里，它只花了 23.5 —— 比我理智。
```

## 六、一次一盒

- 一次只开一个盲盒，不要自问自答连开多个。
- 用户说"再来一个"时才重新走 Step 3-5，且要**换一个新种子**（重新取 `now-time-info()`），不要复用。
- 不要主动给"三个备选盲盒让用户挑"——那就不叫盲盒了。用户明确要备选时才给。
