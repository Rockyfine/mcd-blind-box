# 对话示例

下面是用 WorkBuddy 触发这个 Skill 时的真实交互形态。

> 卡片内容取自**真实运行输出**（离线 fixtures），不是在文档里手写的示意。日期、门店、价格都是示例数据；联网时换成 `--live` 即可得到真实门店。
> 每个示例后面都标了对应的命令行等价写法，方便不装 Skill 也能复核。

---

## 一、最朴素的一句：「随便来一份」

> **用户**：今天不知道吃什么，随便来一份吧

> **助手**（调 `query-nearby-stores` → `query-meals` → `query-store-coupons` → `calculate-price`，然后渲染揭晓卡）：

```
【麦门盲盒 · 纯盲盒】

主品  鳕鱼堡 × 1
配品  麦咖啡拿铁 × 1（饮品）

门店      南京新街口餐厅（到店自取）
原价      ¥37.00
券后价    ¥32.00     使用券：满 25 减 5（满 25.00 减 5.00）
取餐方式  堂食 / 外带（takeWayCode=eat-in）

一句话点评：服务器在 1789000000000 毫秒时点了点头，于是有了这顿。

—— 回复「确认下单」才会真实下单。
   种子 1789000000000 → 第 5 项（主品候选池 11 件；1789000000000 mod 11 = 4）
```

> 等价命令：`python -m mcd_blind_box open --offline --seed 1789000000000`

注意最后两行。**「种子 → 第 N 项」不是装饰**：`1789000000000 mod 11 = 4`，你可以自己算；也可以把同一颗种子重跑一百遍，结果必然一样。这就是这个玩法和「模型随便推荐一个」的区别。

## 二、带约束：「30 块以内」

> **用户**：来一份 30 块以内的

> **助手**：

```
【麦门盲盒 · 预算挑战】

预算      30.00 元
实际      券后 ¥28.00  →  余额 2.00 元
状态      挑战成功

主品  鳕鱼堡 × 1
配品  藤椒风味鸡块 × 1（小食）

门店      南京新街口餐厅（到店自取）
原价      ¥33.00
券后价    ¥28.00     使用券：满 25 减 5（满 25.00 减 5.00）
取餐方式  堂食 / 外带（takeWayCode=eat-in）

一句话点评：服务器在 1789000000000 毫秒时点了点头，于是有了这顿。

—— 回复「确认下单」才会真实下单。
   种子 1789000000000 → 第 5 项（主品候选池 11 件；1789000000000 mod 11 = 4）

注意：本次约束下只放得进 1 件配品，骨架想要 2 件。组合骨架是参考区间而不是硬规则 ——
这里不为了凑数把预算或热量撑破。
```

> 等价命令：`python -m mcd_blind_box open --offline --mode budget --budget 30 --seed 1789000000000`

这里有两件事值得注意：

1. **约束在抽取之前就生效了。** 不是先随便抽一套再看超没超预算，而是先把「加进来一定会超预算」的配品从候选池里剔掉，再在剩下的里面取模。
2. **骨架凑不齐会说。** 预算 30 元的骨架是「1 主品 + 2 配品」，但这家门店的实际价格只放得进 1 件配品。卡上如实写了「只放得进 1 件配品，骨架想要 2 件」—— **不为了凑数把预算撑破，也不假装抽出来的就是标准套餐**。（备注里的件数是按**实际抽到的**配品件数生成的，不会出现「卡上明明有一件配品、备注却说一件都没有」这种自相矛盾。）

## 三、热量挑战：拿不到数据就不给数字

> **用户**：来个不超过 600 大卡的

> **助手**：

```
【麦门盲盒 · 热量挑战】

上限      600 大卡
实际      487 大卡  →  剩余 113 大卡
状态      挑战成功

主品  麦香鸡 × 1
配品  玉米杯 × 1（小食）

门店      南京新街口餐厅（到店自取）
原价      ¥24.00
券后价    ¥24.00     无可用券
取餐方式  堂食 / 外带（takeWayCode=eat-in）

一句话点评：随机来自时间戳，不来自心情。所以你可以复核它。

—— 回复「确认下单」才会真实下单。
   种子 3 → 第 4 项（主品候选池 10 件；3 mod 10 = 3）

营养数据仅供参考，非医疗或健康建议。
```

> 等价命令：`python -m mcd_blind_box open --offline --mode calorie --calorie-max 600 --seed 3`

注意那个「主品候选池 **10** 件」。同一家门店在纯盲盒下是 11 件 —— 少了的那一件是**双层牛肉堡（620 大卡）**，它在热量粗筛这一步就被排除了，不会进候选池。热量约束和预算约束一样，**在抽取之前**就生效。

热量数据来自 `list-nutrition-foods`。如果**某一项匹配不到营养表**，总热量就显示「无法计算」而不是按 0 算：

```
实际      无法计算
```

**绝不估算，更不编造。** 匹配不上就是匹配不上 —— 也正因如此，上限低到没有任何单品能满足时会直接失败：

```
【无法满足约束】没有单品热量低于 5 大卡的餐品（或营养表里匹配不到）。
可以放宽热量上限，或换成不设热量限制的盲盒。
```

（退出码 6；等价命令 `python -m mcd_blind_box open --offline --mode calorie --calorie-max 5`）

## 四、叠加约束：「30 块以内要辣的」

> **用户**：30 块以内，要辣的

> **助手**（模式取交集：预算挑战 + 口味挑战）：

```
【麦门盲盒 · 预算挑战 + 口味挑战（辣）】

预算      40.00 元
实际      券后 ¥31.00  →  余额 9.00 元
状态      挑战成功

主品  麻辣鸡腿堡 × 1
配品  藤椒风味鸡块 × 1（小食）

门店      南京新街口餐厅（到店自取）
原价      ¥36.00
券后价    ¥31.00     使用券：满 25 减 5（满 25.00 减 5.00）
取餐方式  堂食 / 外带（takeWayCode=eat-in）

一句话点评：服务器在 1789000000000 毫秒时点了点头，于是有了这顿。

—— 回复「确认下单」才会真实下单。
   种子 1789000000000 → 第 2 项（主品候选池 3 件；1789000000000 mod 3 = 1）

注意：本次约束下只放得进 1 件配品，骨架想要 2 件。组合骨架是参考区间而不是硬规则 ——
这里不为了凑数把预算或热量撑破。
```

> 等价命令：`python -m mcd_blind_box open --offline --mode budget --mode taste --budget 40 --taste 辣 --seed 1789000000000`

注意标题是「预算挑战 + 口味挑战（辣）」，而不是「预算挑战（辣） + 口味挑战（辣）」—— **口味只标注在口味挑战上**，不会污染其他模式标签。

也注意「主品候选池 **3** 件」：口味筛完后只剩香辣鸡腿堡、麻辣鸡腿堡、藤椒鸡腿堡三个主品，取模的分母就是 3，所以 `1789000000000 mod 3 = 1` 能对上。**候选池大小随约束变化，种子与结果的可验算关系不变。**

## 五、下不进去的时候，说清楚为什么

> **用户**：5 块钱以内开一个

> **助手**：

```
【麦门盲盒 · 预算挑战】

预算      5.00 元
实际      券后 ¥13.00  →  超出 8.00 元
状态      挑战未达标（已放宽）

主品  蔬菜沙拉卷 × 1

门店      南京新街口餐厅（到店自取）
原价      ¥13.00
券后价    ¥13.00     无可用券
取餐方式  堂食 / 外带（takeWayCode=eat-in）

一句话点评：随机来自时间戳，不来自心情。所以你可以复核它。

—— 回复「确认下单」才会真实下单。
   种子 1789000055433 → 第 9 项（主品候选池 11 件；1789000055433 mod 11 = 8，为第 8 个候选）

注意：原始种子抽到的组合不满足当前约束，已按步长 7919 顺延到第 8 个候选（种子 1789000055433）。
注意：本次约束下没有任何配品放得进去，所以只开了一件主品。组合骨架（1 主品 + 1 件配品）是参考区间而不是硬规则，这里宁可少一件，也不把预算或热量撑破。
注意：没能在 5.00 元内凑出组合，这是最接近上限的一套（券后 ¥13.00）
```

> 等价命令：`python -m mcd_blind_box open --offline --mode budget --budget 5 --seed 1789000000000`

四条信息同时被说了出来：**换了第几个候选**、**换种子后的实际种子值**、**配品为什么少了一件**、**放宽到了多少钱**。没有一句「已为你精选超值套餐」这种糊弄话。

## 六、口味说错了 / 店里没这个口味

口味关键词是**封闭集合**（辣 / 鸡 / 牛 / 鱼 / 素 / 甜 / 咖啡），说别的会直接被拒，而不是被猜成最接近的一个：

> **用户**：要海鲜的

```
【参数问题】未知口味 '海鲜'；可选 ['咖啡', '牛', '甜', '素', '辣', '鱼', '鸡']
```

> 退出码 2；等价命令 `python -m mcd_blind_box open --offline --mode taste --taste 海鲜`

如果口味合法、但这家门店的在售清单里没有匹配项，则会这样失败：

```
【无法满足约束】在售清单里没有匹配到「鱼」的餐品。可以换个口味，或改成纯盲盒。
```

这条分支**不会**从记忆里翻出一个「经典麦香鱼套餐」来交差 —— 商品编码只能来自 `query-meals` 的真实返回。它在真实门店上很常见（很多店当天没有鱼类或沙拉类在售）；本仓库的示例菜单七种口味恰好都有匹配，所以这条路径由测试覆盖：`tests/test_pipeline_offline.py::TestConstraintDegradation::test_taste_without_match_raises`，它把菜单裁剪到只剩巨无霸后断言必然失败。

## 七、最关键的一段：确认门禁

> **用户**：就要这个，帮我下单

> **助手**（先渲染确认面板，然后**停下来**）：

```
【待确认】真实下单
门店        南京新街口餐厅
取餐方式    到店自取
取餐编码    eat-in
品项        鳕鱼堡 × 1 / 麦咖啡拿铁 × 1
原价        ¥37.00
券后价      ¥32.00     使用券：满 25 减 5（满 25.00 减 5.00）
—— 回复「确认下单」才会真实下单，回复其他内容则不下单。
```

> **用户**：看起来不错

> **助手**：还没有下单。需要我下单的话，请回复「**确认下单**」。
> （「看起来不错」只是对内容的认可，不构成下单指令。）

真的确认之后（离线下会返回一张带 `offline` 标记的假订单，**不产生真实交易**）：

```
> **用户**：确认下单

下单成功：订单号 OFFLINE0001
状态：待支付
来源：fixtures（离线假订单，未产生真实交易）
```

> 等价命令：`python -m mcd_blind_box order --offline --confirm --seed 1789000000000`（离线；联网去掉 `--offline` 才是真下单）

判定规则被编码成了可测试的函数，顺序本身就即规则：

| 用户说 | 判定 | 理由 |
|---|---|---|
| `确认下单` / `帮我下单` / `买了` | ✅ | 明确下单意图 |
| `就这个吧` / `行` / `好吧` / `嗯` | ❌ | 只是认可内容 |
| `如果可以的话就下单` | ❌ | 条件式表达 |
| `多少钱？` / `能下单吗` | ❌ | 提问 |
| `不确认` / `先别下单吧` | ❌ | 否定表达 |
| `随便` / `再看看` | ❌ | **拿不准一律判为不确认** |

命令行这一侧更硬：`order` 子命令**没有 `--confirm` 就连数据源都不构造**，直接退出码 3。

## 九、联网时的两件真实情况

### 得来速门店「搜不到」

> **用户**：用来得速开一个

> **助手**：按当前位置附近没有搜到可点餐的得来速门店（`searchType=1` 返回空列表，这在很多城市都正常）。换关键词搜索试试：

```
python -m mcd_blind_box open --live --scene dt --city 武汉市 --keyword 得来速
```

> 结果：

```
门店        1960220 武汉东风大道得来速餐厅
beCode      196022041
取餐方式  得来速（takeWayCode=take-dt-quick）
```

**不重试同一个请求**，而是换成按城市 + 关键词搜 —— 这是数据条件，不是可以靠重试解决的问题。

### 商品券的优惠算不出来

> **用户**：我有个「中薯条买一送一」的券，能用吗？能省多少？

> **助手**：这张券确实在可用列表里，但它**只有当购物车里真的有中薯条时才会生效**。而且它没有「满 X 减 Y」这样的数字 —— **实际抵扣多少由服务端算价决定，我这边算不出来，所以不会给你编一个数**。下单前我会用它去问一次真实算价，到时以服务端返回的金额为准。

如果本地展示必须给个数，卡上会标注「商品券，实际抵扣以服务端算价为准」，而不是把它说成 0 元优惠、也不是假装知道它值多少钱。
